# Making a release

What `/patch`, `/minor` and `/major` do, once they have said how the version goes up. The README's "Releasing" says how a release is published; this is everything up to that.

1. **Start from GitHub's.** On `main`, up to date with GitHub (`git pull --ff-only`). Work in progress is left uncommitted: it goes out in the release's own commit, with its release notes, so the change and what is said of it are one commit. Say what is uncommitted, and leave out anything that was only ever temporary (a scratch test, a probe, a file of notes), as `/commit` would.
2. **The new version.** From `package.json`'s, bumped as asked. Set it with `npm version <version> --no-git-tag-version`, which changes `package-lock.json` too.
3. **Draft the release notes**, `docs/release-notes/<version>.md`: what has changed since the last release (`git log v<previous>..HEAD`, and the diff where a subject doesn't say enough; every commit if there is no tag yet), and what is uncommitted (`git status` and `git diff`). No title, then `## New`, `## Improved` and `## Fixed`, each left out if it has nothing, bullets in the README's voice - what someone using it would notice, not how it was done. Keep them concise: a bullet a change, a line each, saying what it does, not every case it covers or what it was before. Anything that changes what's written to people's tables, or that they need to do, gets a `## Before updating` at the top. If they have already been written, during the work or by hand, they are a draft like any other: check them against all of that, add what they miss, and still stop and ask at step 7. Nothing is taken as read because it is already there.
4. **Bring the README up to date** with anything new or changed in this release, in its own voice.
5. **Check it, and take the pictures**: `npm run check`, all of it, and `npm run dist:mac` (both Macs, the Intel one tried under Rosetta) if what gets packaged has changed. Then `npm run screenshots` and look at each one: the store shows the pictures as they are at the release's tag, so they go in the release's commit. Stop and say what fails rather than release around it.
6. **Spell and grammar check them.** Read the release notes and every changed line of the README for spelling, grammar and punctuation: UK spelling, single dashes, its voice, names of settings as the app and config show them. Don't change them yet: list each fix proposed, what it was and what it would be.
7. **Stop and ask for the release notes and the README to be checked**, however they came to be written. Show the release notes in full, what changed in the README (`git diff README.md`) and the spelling and grammar fixes proposed, and ask for them to be read before anything is committed: make the fixes agreed and whatever else is asked, and show them again. Commit nothing until told they are right.
8. **Carry their wording through.** Once the release notes and the README are agreed, with the fixes and any rewording asked for, use the same words for the same things everywhere else: the app's labels, hints and messages, the command line's, and the comments in the code and tests. Look for each thing they now name or describe differently (a button, a setting, a place) and change the old wording to match, keeping what the code says of itself where it means something else. Then `npm run verify` again, and the end-to-end tests for any text they look for; say what was changed.
9. **Commit it and push it**, as `/commit` does, the work in progress and the release in one commit: a short, witty subject ending `; <version>`, the detail of all of it in the body. Pushing the commit publishes nothing; the GitHub release does.
10. **Stop and ask before publishing**: whether to make the GitHub release, as that is what publishes to npm and builds the app. Only once told to: `gh release create v<version> --title "v<version>" --notes-file docs/release-notes/<version>.md`.
