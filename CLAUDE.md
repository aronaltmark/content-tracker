# Content Tracker

Tracks the folders and files of a project on Airtable or Google Sheets. It's to be listed at https://store.generativenoise.com/tools/content-tracker (gn-site), which Airtable's registration also gives as its home page. It's published to npm as `@generativenoise/content-tracker`, with an Electron app for Mac, Windows and Linux. See README.md for what it does and how it's set up.

- `core/` is the logic and has no idea how it's being run: it never imports from `cli/` or `gui/`, never prints, and logs through the `logger` it's given. Anything both the command line and the app need belongs there.
- `cli/` and `gui/` only wrap `core/`. `dependencies` is what `npx` installs, so it's only what `core/` and `cli/` use: Electron, Vue and the build tools stay in `devDependencies`.
- `gui/` is a sandboxed page with no Node. It only reaches the rest through what `gui/preload/index.js` exposes, the main process checks who's asking (`handle` in `gui/main/index.js`), and the token never goes to the page. Keep all of that true of anything new.

## At the start of a session

Run `/pull` in full before anything else, unless it has already been run this session: whatever was asked for waits until it has said what it found.

## Rules

- Never read, print or copy `config*.json`, `.env` or a service account key: they hold live tokens. Show a config's shape from `core/config.js` or the README. To try something end to end use `e2e/fake-airtable.mjs`; talking to a real Airtable base or spreadsheet is asked for first.
- What's written to a table is what people's rows are matched on. A change to `_path`, or to how any field is worked out, can update, or delete and recreate, every record in someone's table, taking their own columns with it: treat it as a breaking change, say so in the release notes, and check the old and new against real media first.
- Removing records is the dangerous part of this. Anything that could make a scan come back short (a drive gone, a folder unreadable) must end up in `.errors`, so nothing is removed that time.
- Signing in (`core/oauth.js`) is the browser to a server on this computer, with PKCE and a state checked on the way back. The app's registrations are in `core/oauth-clients.js`, public by design, but Google's client secret is kept out of git all the same, as Google may reset one it's told was published: it's in `core/oauth-secret.js`, which `npm install` writes from `GOOGLE_CLIENT_SECRET` (and the release from the repository secret of that name) - never paste it into a tracked file; a sign in's tokens are kept only in the keychain (the app) or a file only the user can read (the command line), never in a config or the page. Airtable's refresh tokens work once, so a new one is kept every time it's refreshed. `e2e/fake-google.mjs` stands in for both, and for Sheets: try against that, never a real account unless asked.
- Updating (`core/updates.js`, `gui/main/updater.js`) only ever installs a download that matches the sha256 GitHub gives for it, and only from this repository's releases. The tests never ask the real npm or GitHub: `e2e/fake-releases.mjs` stands in for both.
- Anything sent to a Sheet stays `RAW`, so a file name can't run as a formula.
- Airtable and Google Sheets stay interchangeable: anything new a target has to do goes on both, behind what `core/targets/index.js` lists.
- Every config setting is in `core/config-schema.js`, with its default and a short description: that's what a config is checked against, what fills in what's left out, and, once `npm run schema` has written `core/config.schema.json`, what editors help with. A setting that's renamed goes in `RENAMED` in `core/config.js`, so an old config says what to change.
- Paths stay portable: Mac and Windows both. Use `path` for anything on disk, `path.posix` for anything sent to a table, and nothing that only works with one kind of separator, in the tests too.
- Every setting in the app gets a hint, unless it says all there is to say by itself: one that only repeats its label is noise.
- A hint or tooltip is as simple as it can be: a short sentence of what the thing does, in everyday words, not every case and condition it meets. The README is for the rest. That goes for the ones already there too: one that says more is cut down when it's next touched, or when asked.
- User-facing text and comments use single dashes, never double.
- Colours live in the `:root` tokens of `gui/renderer/src/style.css` only.
- A release needs `docs/release-notes/<version>.md`; `npm run verify` must pass.
- From 1.0.0, a config that works keeps working, and the app's saved settings keep loading: a change that breaks either, or anything else people rely on (the command line's options, what's written to their tables), is a major version, with what to do in the release notes' `## Before updating`. An old config that would silently do something different is never acceptable, even in a major version: it fails with a clear message instead.
- The app shows every version's release notes, from `docs/release-notes/`, under the version beside its name.
- While working, run the tests for what changed with `npm run verify` (`npx playwright test e2e/<file>.e2e.js`, or `-g "part of a name"`). Before a commit, run what it could change, unless it has all passed since:
  - **Everything** (`npm run check`: verify, then every end-to-end test) for `core/`, `cli/`, `gui/`, the packages, or the build and test config.
  - **`npm run verify` and those files** for changes only to test files.
  - **`npm run verify` alone** for anything else: `.claude`, the README and the workflows.
- A change to what gets packaged (`electron-builder.yml`, ffprobe, the packages) is also tried in a packaged build (`npm run dist`, then `/install`): ffprobe working from source says nothing about it working from inside the app. Intel Macs too, where it changes ffprobe or the build: `npm run dist:mac` builds both, and the Intel one runs here under Rosetta.
- The Mac app is signed ad hoc, the whole of it (`identity: '-'`, with `hardenedRuntime: false` until it's notarised), as EM Calc's is: unsigned, or with only the linker's signature on the program, a downloaded copy is "damaged" and can't be opened at all. A build that changes the packaging is checked with `codesign --verify --deep --strict` on the `.app`, and the DMG it's in tried as a download would be (marked with `com.apple.quarantine`), as a copy built here opens whatever its signature.
- The icon is `build/icon.svg`, a table's three rows, each a short dash and a long one, the first dash an eye, on a tile that is itself the folder: the squircle with its top stepping down after a small tab, as the Finder's folder has it (worked out from the superellipse, n=5, by `scripts/icon-outline.mjs`, which `npm run icons` writes into both SVGs: change the shape there), its style the plugins' (the kit's squircle and the logo's field of squircles) but dark, with the blue in the mark, as it's an app of its own. The menu bar's icon is `build/tray.svg`, the tile in outline with the rows filling it, in black, for the Mac to colour. `npm run icons` makes `build/icon.png` and `build/trayTemplate.png` (and `@2x`) from them, and the DMG's window, `build/background.tiff`, from `build/dmg-background.svg`, its arrow level with the icons `electron-builder.yml` places (on a Mac, as it needs `tiffutil`); commit them all.
- The pictures are `docs/screenshots`, taken by `npm run screenshots` (`scripts/screenshots.mjs`): the real app against the stand-ins, in a Mac window, and the menu bar and the tables drawn as mock-ups, as they aren't the app's to show. Don't take them again while the app's look is being worked on, as each change would mean another round: leave them until the design is settled, or a release is being made, and take them all then. To look at a change meanwhile, `npm run screenshots -- <a scratch folder>` takes them there instead. Take them all as part of each release, in its own commit (`.claude/release.md`): the store shows them from the release's tag, so what's committed is what it shows. A picture never shows anything from this computer: no real paths, accounts or bases.
- About's GN logo is `gui/renderer/src/assets/gn-logo.svg`, from `gn-logo-2026`'s exports: changing it, or using the logo anywhere else here, updates that repo's "Where the logo is used" table.
- Help is `docs/help.md`, which is also the README's App section: change it there, then `npm run readme`.
- Licensed GPL-3.0-or-later, held by Generative Noise. A new dependency that ships (`dependencies`, or anything in the app) has to be compatible with it, and anything bundled that isn't ours, like ffprobe, gets a line in the README's Licence. About lists every package the app includes, from `package-lock.json`, and a test fails if one's licence isn't on the list of those the GPL can include (`scripts/licences.mjs`).
- Commit messages are short, to the point and witty if possible, with all the detail in the body; one that changes the version has it in its subject (`Fonts all the way down; 0.2.0`). Commit messages never carry a `Co-Authored-By` line, or any other attribution to Claude.
- `/commit` commits that way, and pushes. `/patch`, `/minor` and `/major` make a release, the version up 0.0.1, 0.1.0 or 1.0.0, with its release notes drafted and everything else it needs (`.claude/release.md`), stopping before it is published. `/pull` brings in changes from git and flags anything new from `npm audit`. `/install` builds the app for this computer and opens it.
